# Portal_Mensajeria

Panel web multi-cliente del bot de WhatsApp (`../Bot_Mensajeria`). Cada Cliente (comercio) entra con sus usuarios y ve sus pedidos, artículos, chats, consultas, escalamientos e integraciones. Mismo deploy y mismo link para todos.

Excepción: **Aguirre SRL** (Cliente 4, `Clientes.tipoNegocio = 'pasajes'`) no usa el portal: tiene el módulo WhatsApp IA dentro de su sistema (`../AguirreSRL`, `Views/WhatsAppIA/CLAUDE.md`), que llama a **los mismos `usp_Portal_*`** de chats, humano solicitado, aprendizajes y `ClienteCampoSet/Obtener`. Si cambiás parámetros o columnas de esos procedures, revisá también `ControladorWhatsAppIA.cs` de AguirreSRL. Su estilo (`css/WhatsAppIA/Portal.css`) es una copia generada de `client/src/styles.css`.

Stack: backend Node 22 + Express 5 (API JSON en `/api`), frontend React 19 + React Router 7 compilado con Vite (`client/`), Azure SQL vía `mssql` (sin ORM), sesiones de `express-session` guardadas en la tabla `Sesiones` (`src/services/sesionStore.js`, sobreviven a los deploys). Deploy en Railway (un solo servicio: corre `npm run build` y después `npm start`). Sin tests automatizados.

Desarrollo: `npm run dev` (Express en `PORT`, default 3100) + `npm run dev:client` (Vite en :5173, pasa `/api`, `/shopify` y los callbacks de OAuth a Express). `client/dist` lo genera el build y no se commitea.

## Reglas fijas

- **SQL**: nunca crear archivos `.sql` en el repo ni ejecutar DDL/DML contra la base. Todo script nuevo se agrega al final de `D:\SQL Scripts\Bot_Mensajeria.sql`, debajo de `---------------CAMBIOS CLAUDE`, con encabezado `-- [AAAA-MM-DD] Descripción`, idempotente (`IF OBJECT_ID(...) IS NULL`, `IF COL_LENGTH(...) IS NULL`) y con `GO` entre bloques. El usuario lo corre en SSMS. Si el código nuevo lee columnas nuevas, avisar: **correr el SQL antes de deployar**. Ver la skill `sql-cambio`.
- La base es **compartida con Bot_Mensajeria** (`Clientes`, `Articulos`, `Stock`, `Pedidos`, `DetallePedidos`, `Mensajes`, `Escalamientos`, `ConsultasArticulo/Pedido`, vista `VConsultas`). No renombrar ni borrar columnas que use el bot; el bot busca artículos por `nombre` exacto con `activo = 1`.
- **Multi-tenant**: toda ruta de datos va bajo `/clientes/:clienteId/...` con `requireAuth` + `resolveClienteAccess` (admin entra a cualquiera, rol `cliente` solo al suyo) y **toda query filtra por `clienteId`**. `requireAdmin` para lo que solo ve el admin.
- **Todo el SQL va en stored procedures** (`CREATE OR ALTER PROCEDURE dbo.usp_<App>_<Accion>`, en el mismo `Bot_Mensajeria.sql`), y el código solo los llama con `ejecutar('dbo.usp_...', { param: [sql.Tipo, valor] })` de `src/services/db.js`. Escrituras de varios pasos: `SET XACT_ABORT ON` + `BEGIN TRY/BEGIN TRAN ... COMMIT` + `CATCH ROLLBACK; THROW`. Listas → un parámetro JSON + `OPENJSON`. El bot y el portal están migrados enteros: no hay `.query()` ni `new sql.Transaction` en `src/` (`getPool()` solo se usa en `index.js` para conectar al arrancar). Para cambios chicos de una sola columna hay procedures con selector (`usp_Portal_ClienteCampoSet @campo`, `usp_Portal_ShopifyConexionCambiar @accion`).
- **Fechas en hora de Argentina**: en tablas/columnas nuevas, `DATEADD(HOUR, -3, GETDATE())` (el servidor está en UTC). Las tablas viejas (`Mensajes`, `Pedidos`, `Escalamientos`, `Chats`...) siguen en UTC y el portal las convierte con `Clientes.zonaHoraria`: no mezclar. `Logs.fecha` ya está en hora Argentina.
- Copy de la UI en español rioplatense (voseo). Toasts en Title Case: la API responde `{ ok, tipo: 'success'|'warning', mensaje }` (helpers `ok`/`aviso`/`falla` en `api.js`) y el frontend lo muestra con `useAvisar()`. `setFlash` queda solo para el flujo de Shopify que navega el navegador (lo lee `/api/sesion`).
- Sin dependencias nuevas salvo necesidad real (usar `fetch` y `crypto` nativos).
- Commits solo cuando el usuario lo pide; mensajes en inglés.

## Seguridad (no romper)

- **CSRF**: todo lo que no sea GET en `/api` exige el header `X-Requested-With` (lo pone `api()` de `client/src/lib/api.js`; no hacer `fetch` directo) y rechaza `Sec-Fetch-Site` de otro sitio. Solo se parsea JSON (no hay `express.urlencoded`). `/api/interno/eventos` queda afuera (Bearer del bot).
- **Sesión**: `requireAuth` revalida usuario y Cliente cada 30 s (`usp_Portal_SesionValidar`): usuario borrado/inactivo, Cliente inactivo o contraseña cambiada (`Usuarios.passwordCambiadaEn` vs `session.passwordMarca`) → 401; rol/Cliente cambiados → se actualiza la sesión. Después de cambiar usuarios/Clientes llamar `invalidar()` y `eventos.cerrarUsuario/cerrarCliente`.
- Login: bcrypt costo 12 (los hashes viejos se rehacen al entrar), mínimo 10 caracteres, tope de intentos fallidos por IP y por email (`limiteService`).
- `index.js` pone CSP y headers de seguridad: si se suma un recurso externo (script, fuente, iframe), agregarlo a la CSP. Cookie `portal.sid` con `secure: 'auto'`.
- Webhooks de Shopify: solo valen si los firmó la app de esa conexión. `router.param('id')`: todos los `:id` son enteros.

## Mapa

- `index.js`: orden de montaje importa. `shopifyRoutes.webhookRouter` va **antes** de los parsers y la sesión (firma sobre body crudo). Después: estáticos de `client/dist` y `public/`, `express.json`, sesión, `/api` (`routes/api.js`), `shopifyRoutes.publicRouter` (`/shopify`, `/shopify/callback`) y al final el fallback que devuelve `client/dist/index.html` para cualquier otra ruta (React resuelve la página).
- `src/routes/api.js`: toda la API JSON (sesión/login, clientes, usuarios, negocio, artículos + importación Excel, chats + polling `/chats/novedades`, escalamientos, pedidos, consultas, integraciones/Shopify). `src/routes/shopify.js`: solo webhooks + instalación/OAuth.
- `src/middleware/requireAuth.js`: en rutas `/api/` responde 401/403 JSON; en el resto redirige.
- `src/services/`: un servicio por tabla/feature (`pedidoService`, `articuloService`, `chatService` (`huellaBandeja` para el tiempo real), `importService` con jobs en memoria + polling, `flash`, `db.getPool()`, `eventosService`). `metaService`: al crear un Cliente, busca su WABA entre las compartidas con el Tech Provider (`GET /{businessId}/client_whatsapp_business_accounts?fields=id,phone_numbers{display_phone_number}`, matcheando por teléfono; también al cambiarle el teléfono) y la suscribe (`POST /{wabaId}/subscribed_apps`) — si no la encuentra o la suscripción falla, no se crea el Cliente (el cliente externo tiene que haber completado el Embedded Signup antes). Shopify: `shopifyClient` (token + GraphQL), `shopifyAppService` (credenciales de apps en DB), `shopifyOAuthService`, `shopifySyncService`, `shopifyOrderService`, `shopifyWebhookService`, `cryptoService` (AES-GCM, clave derivada de `SESSION_SECRET`). `logService`: tabla `Logs` compartida con el bot (cola en memoria + insert por lotes, captura `console.warn/error`, purga lo de más de 7 días); `api.js` loguea toda request no-GET, los GET con error o de más de 1 s, y login/logout. Página `/logs` solo admin. `src/viewHelpers.js`: `numero()`, lo usa `chatService`.
- `client/src/`:
  - `main.jsx` (router de datos + providers) y `App.jsx` (todas las rutas; `<Privada admin>` para lo que solo ve el admin).
  - `pages/`: una por pantalla.
  - `components/Layout.jsx`: menú lateral (lista `GRUPOS`, agregá ahí las páginas nuevas); `useCliente()` da el Cliente que se está viendo.
  - `components/ui.jsx`: `PageHead`, `PageHelp`, `Stats`/`Stat`, `Empty`, `TablaCargando`, `ErrorCarga`, `Pagination`, `Contacto`, `useTitulo`.
  - `components/`: `Toasts.jsx` (`useToast`, `useAvisar`), `Confirm.jsx` (`useConfirm`), `Modal.jsx` (`<dialog>` nativo), `Form.jsx` (validación con toasts), `BotSwitch.jsx`, `ShopifySync.jsx`, `ImportarExcel.jsx`, `DetalleArticulo.jsx` (modal con fotos y toda la info del artículo; lo de Shopify sale de `Articulos.shopifyDatos`, el JSON completo que guarda el sync).
  - `lib/`: `api.js` (`api()` y `useApi()`), `auth.jsx`, `format.js` (`numero`, `fecha`, `plata`, `iniciales`), `icons.js` (SVGs genéricos, sin logos de marcas; se usan con `<Icon name="x" />`), `timezones.js`.
- `client/src/styles.css`: un solo CSS con secciones `/* ── Nombre ── */` y variables en `:root`. Patrón de página: `.page-head` (h1 + `.page-sub`), ayuda larga en `PageHelp`, números en `.stats`. `public/`: favicon y plantilla de Excel.
- `docs/SHOPIFY.md`: cómo funciona la integración con Shopify.
- **Tiempo real (SSE, sin polling)**: cada pestaña abre un `EventSource` a `GET /api/clientes/:id/eventos` (`eventosService`, en memoria: asume una sola instancia). Avisan el bot (`POST /api/interno/eventos` con `Bearer BOT_API_TOKEN`, desde su `portalAvisoService`) y el propio portal (middleware en `api.js` para los POST de chats/escalamientos/humano-solicitado/pedidos, y los webhooks de pedidos de Shopify). Tipos: `mensaje`, `chat`, `revision`, `escalamiento`, `pedido`. Los eventos solo dicen "cambió X": en el cliente `useEnVivo(tipos, recargar)` de `lib/eventos.jsx` (conexión abierta en `Layout.jsx`) vuelve a pedir con los endpoints de siempre; si la conexión está caída hay respaldo cada 60 s, y al volver a la pestaña refresca. Pantalla nueva que deba actualizarse sola: usar `useEnVivo`, no `setInterval`. `alCambiar` recibe los eventos agrupados (ej. `chat` con `userId`). `contadores`, el resumen de Inicio y la huella pasan por `cacheCorto` (3 s por Cliente, se invalida en cada `eventos.emitir`). El `EventSource` se cierra en `pagehide` (si no, quedaban conexiones colgadas).
- **Revisión humana**: el bot pausa el chat (`Chats.botActivo = 0`, `Chats.revisionHumana = 1`) cuando piden una persona o insultan, y avisa por WhatsApp a `Clientes.telefonoAlertas` (se edita en Mi Negocio). En el portal: estado `revision` en `chatService`, `revision`/`revisionChats` en `/contadores` (franja roja + toast + título en `Layout.jsx`). En la UI: página **Atención Humana** (`/atencion-humana` = `<Chats modo="humano">`: la misma bandeja de `Chats.jsx` con la lista de `GET .../humano-solicitado` y la conversación/envío de `/chats/:userId`). Los `Escalamientos` en la UI se llaman **Reclamos** (`/reclamos` = `<Chats modo="reclamos">`: un chat por número desde `GET .../reclamos-bandeja` (`usp_Portal_ReclamosBandeja`), con sus reclamos y el selector de estado arriba del historial). Estado Pendiente (`revisionHumana = 1`) / Atendido (`revisionHumanaAtendidaEn/Por`), procedures `usp_Portal_HumanoSolicitado*`. Pasa a Atendido solo al responder desde el portal o desde el celular del negocio (coexistencia: el bot recibe `smb_message_echoes`), al reactivar el bot o a mano (`POST .../humano-solicitado/:userId/estado` o `.../revision/atender`). Reactivar el bot en un chat pausado (`usp_Portal_ChatBotSet`) guarda `Chats.historialDesdeId`: el bot solo le pasa a Claude los mensajes posteriores, para que no relea un pedido de persona viejo y se vuelva a pausar.
- **Links de compra** (`/links-compra`, `linkCompraService`, tabla `LinksCompra`, interruptor `ShopifyConexiones.linkCompra` en Integraciones): con Shopify conectado el bot usa la tool `enviar_link_compra` en vez de `crear_pedido` y manda el cart permalink de la tienda con un token (`attributes[whatsapp]` + `ref=wa-<token>`); el link lo agrega el código, no Claude. Los webhooks de órdenes lo vinculan por el token (`usp_Portal_LinkCompraVincular`): `enviado` → `comprado` → `pagado` | `cancelado`. Las órdenes de links no son `Pedidos`. Ver `docs/SHOPIFY.md`.
- **Aprendizajes** (`/aprendizajes`, `aprendizajeService`, tabla `Aprendizajes`): pares pregunta → respuesta que carga el negocio (a mano o con "Enseñarle esto al bot" en las burbujas de respuestas humanas de `Chats.jsx`, modal `AprendizajeForm.jsx`). El bot los suma al final de su system prompt (`usp_Bot_AprendizajesActivos`, orden fijo por id para no romper la caché). Tope de 50 activos. El bot no aprende solo de los chats.
- **Dashboard** (`/dashboard`, `dashboardService` + `metaAdsService`): rentabilidad tipo Escalafy. Copia las órdenes de Shopify a `ShopifyOrdenes`/`ShopifyOrdenItems` (con el `unitCost` de cada variante; si la orden se copió sin costo, `usp_Portal_DashboardDatos` usa el `Articulos.costo` actual de la variante; primera vez un año para atrás, después incremental por `updatedAt` con cursor en `ShopifyOrdenesSync`; los webhooks `orders/*` llaman a `programarSync`). El gasto de Meta Ads va por campaña y día a `MetaAdsDiario` (cuenta + token propio cifrado en `MetaAdsConexiones`; sin token usa `WHATSAPP_ACCESS_TOKEN`). Costos que Shopify no sabe en `DashboardConfig`. Todo se lee con `usp_Portal_DashboardDatos` y las métricas (ganancia, ROAS, ROAS de equilibrio…) se calculan en `dashboardService.calcular`. Las syncs corren en segundo plano al abrir la página; la página re-pide cada 4 s mientras `sincronizando`. **Todo en USD**: `cotizacionService` trae la cotización de cada día de currency-api (jsDelivr, sin clave) y la guarda en `CotizacionesDolar` (global); `DashboardConfig.cotizacionUsd` la fija si el negocio quiere; los montos de Costos se cargan en USD. **Mercado Pago** (`mercadoPagoService`): `/v1/payments/search` por `date_last_updated` con cursor → `MercadoPagoPagos` (`costo` = monto − neto recibido: comisión + cuotas + retenciones); con MP conectado la comisión es la real y el % de Costos solo se aplica a lo que no pasó por MP. **Conexión por OAuth** (botones del Dashboard): `POST .../meta-ads/oauth` y `.../mercadopago/oauth` devuelven la URL (state de `oauthStateService`), vuelven a `/meta/callback` y `/mercadopago/callback` (`routes/conexiones.js`, toast con `setFlash`); Meta con varias cuentas deja el token cifrado en `session.metaPendiente` y el Dashboard abre el selector (`?meta=elegir`). Sin las variables de OAuth queda la carga manual (cuenta + token / Access Token `APP_USR-`).
- **Horario del bot** (Mi Negocio, `PUT .../negocio/horario`, `usp_Portal_ClienteHorarioBot(Set)`, columnas `Clientes.horarioBotDesde/Hasta` en hora Argentina, NULL = 24 hs): fuera de horario el bot guarda y no responde; a la apertura responde lo pendiente (`horarioService` del bot).
- **Estado del chat**: se calcula en `CHATS_CTE` (`estadoAuto`); `Chats.estadoManual` (lápiz en el header, `EstadoChat.jsx`, `POST .../chats/:userId/estado`) lo pisa hasta volver a Automático. Humano Solicitado siempre gana.

## Variables de entorno

`SESSION_SECRET`, `DB_SERVER`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, `DB_PORT`, `PORT`, `WHATSAPP_ACCESS_TOKEN` (mismo token de Tech Provider que usa Bot_Mensajeria), `META_BUSINESS_ID` (ID del Business Portfolio del Tech Provider). Opcionales: `APP_URL`, `TOKEN_ENC_KEY`, `SHOPIFY_API_VERSION`, `SHOPIFY_SCOPES`, `META_API_VERSION` (default `v25.0`), `META_APP_ID` + `META_APP_SECRET` (+ `META_ADS_CONFIG_ID` si se usa Facebook Login for Business) para "Conectar con Facebook" en el Dashboard (redirect `{APP_URL}/meta/callback`, permiso `ads_read`), `MP_CLIENT_ID` + `MP_CLIENT_SECRET` para "Conectar con Mercado Pago" (redirect `{APP_URL}/mercadopago/callback`), `BOT_URL` + `BOT_API_TOKEN` (para responder chats a mano desde Mensajes: el portal llama a `POST {BOT_URL}/portal/enviar`; el token tiene que ser igual al `PORTAL_API_TOKEN` del bot; el mismo token autentica los avisos de tiempo real que manda el bot, que necesita `PORTAL_URL` apuntando al portal). Las credenciales de Shopify se cargan desde el portal (tabla `ShopifyApps`), no en Railway. Cambiar `SESSION_SECRET` invalida los tokens de Shopify guardados.

## Cómo trabajar

- Leer solo lo necesario: `Grep` para ubicar, `Read` con `offset/limit`. No releer archivos ya leídos en la sesión.
- Para verificar sin tocar la base real: skill `probar-cambios`. Para páginas nuevas: skill `nueva-pagina`.
- Respuestas cortas y en español.
